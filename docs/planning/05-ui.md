# Planning v1 — 05 UI

The spec for the `ui` repo (GitHub `sp-ui`, Angular 19, branch from `stage`). Backend contracts are
in `04-api.md`. `mockup.html` in this folder shows the intended behavior with mock data; open it in
a browser. Where the mockup and this file disagree, this file wins. The mockup's visual style is
not the target: build with the repo's `ave-*` atoms, theme tokens and grid styles.

Read first, in the ui repo: `CLAUDE.md`, `.claude/CLAUDE.md`, `docs/development-workflow.md`, and
`src/app/plans-actions/README.md` (the newest module and the pattern to follow).

## 1. Ground rules from the repo

- Angular 19, standalone `OnPush` components, a thin routing `NgModule` lazy-loaded from
  `src/app/dashboard/dashboard-routing.module.ts`. State in RxJS `BehaviorSubject` services;
  `@UntilDestroy()` + `untilDestroyed(this)`.
- npm only (`npm ci --legacy-peer-deps`). Do not add dependencies; everything needed is installed
  (AG Grid Enterprise 35, PrimeNG 18, Chart.js 3 via `<p-chart>`, Luxon).
- **One GraphQL endpoint.** Planner functions are on the app's Hasura API with everything else.
  Call them through `ZeusService` and the generated Zeus client, as every module does
  (`npm run pull-latest-zeus` after the metadata is live; never hand-edit generated files). There
  is no planner endpoint, second client or new environment key.
  - The app's endpoint is itself being replaced by a new Hasura (`07-hasura-rebuild.md`). That is
    one change to `graphql_uri` in the environment files, made in package H4, not planner work.
    Never write the API host anywhere else.
- Reads are query functions called with an `operationName` (`Planning<Verb><Noun>`), no `@cached`.
- **Writes are mutations** named `planning_<name>`. Below, "the `x` command" means the `planning_x`
  mutation, called through `PlanningApiService.run('x', args)`.
- Impersonation works as in the rest of the app (the gateway endpoint); copy the
  `PlansActionsSessionService` pattern and add nothing planner-specific.
- A failed command comes back as a GraphQL error whose message is written for the user
  (`check_violation` passes through); show it with `toUserMessage`. Nothing was saved.
- Months are **month keys**: the 2nd of the month (`2026-07-02`), the database's convention. Treat
  them as opaque month identifiers; label them with Luxon; never assume day 1. Any day of a month
  may be sent; the backend normalizes.
- Do not read Hasura roles and do not build a role concept. Everyone is `user`; what a person may do
  arrives as capability booleans from `planning_get_models` (§3).
- Function arguments go in `{ args: { … } }`; arrays are Postgres literal strings. Use
  `toPgTextArray` from `src/app/utils/pg-array.ts` (do not add a fifth implementation).
- UI kit: `ave-*` atoms from `src/app/shared/atom/`; Lucide icons via `ave-icon`; no Angular
  Material; no dark mode. Style with preset tokens first, scoped SCSS second.
- No hard-coded `id`, `for` or `inputId` in templates (`uniqueId('<component>')`); `data-pf` anchors
  on navigable elements; icon-only buttons need `ariaLabel`.
- Luxon for dates. Show hotel names through the existing display-name helpers (demo masking).
- New modules must work on a phone. See §9.
- Tests are Jest specs beside the code. CI runs Jest and the build.
- PRs go to `stage`, squash-merged; the PR title is a Conventional Commit of 72 characters or fewer;
  follow the repo's rule on commit message content.

## 3. Gating and navigation

All of these, or the module is either invisible or unprotected:

1. `src/app/services/user.service.ts`: add `'planning'` to `MODULE_ENTITLEMENTS`.
2. `PlanningAccessService.isEntitled()` = `userService.isAlphaFeaturesUser && userService.hasModuleEntitlement('planning')`,
   with `access$` re-evaluated on `user$`.
3. Route in `dashboard-routing.module.ts`: path `planning`, `canActivate: [PlanningAccessGuard]`,
   `loadChildren`. The guard returns `true` or `UrlTree('/exec')`.
4. Sidebar (`src/app/dashboard/app.sidebar.component.ts`): add the item to every array Plans &
   Actions appears in (six), with `data: { lucide: … }`, filter it out in the constructor when
   `!hasAccess()`, and add it to `NAV_PF_ANCHORS` and, for detail routes, `NAV_DETAIL_ROUTES`.
5. `src/app/shared/product-fruits/pf-anchors.ts`: register the routes (`pf-anchors.spec.ts` enforces it).

Inside the module, show and hide controls from the capability booleans on `planning_get_models`
(`can_update`, `can_create_scenario`, `can_lock`, `can_update_chart`, `can_update_model`,
`can_read_ledger`, `can_read_standard`, `can_update_standard`). Permissions are app-wide and
module-based; the planner has no roles of its own.

UI gating hides the module. The backend enforces access on every call (`04-api.md` §1.1), so a
"not allowed" error from a call is a real state to render, not a bug.

## 6. Workspace

The P&L is the editor. One grid, one drawer.

### 6.1 Data

- Lines: `planning_get_workspace(property_code, scenario_id, compare_version, plan_year)`.
- Subtotals and KPIs: the existing twelve-month financial query
  (`src/app/services/api/db-pointer-query/`, the service behind Detailed Financials' multiperiod
  view) with `version = scenario.version_key`, `compare` = the compare key, for the hotel. Use the
  row layout of the existing Detailed Financials domain files (`src/domain/detailed-financials/`)
  for which USALI subtotal rows exist per department, so the workspace and Detailed Financials agree.
- KPI strip: Occupancy, ADR, RevPAR, Total revenue, GOP and GOP margin for the year, each with its
  difference from the compare version. From the same query.

Load lines and subtotals in parallel; render when both are in. Use request sequence numbers per
channel (the Plans & Actions stale-response guard) so a slow response for an old scenario never
overwrites a newer one.

### 6.2 Grid

AG Grid Enterprise, `class="ag-theme-balham"`, `spAgDensity`, tree data (`treeData: true`,
`getDataPath`). This is the first tree-data grid in the repo; row grouping is not suitable because
group rows carry their own values (subtotals come from the data layer, with hierarchy weights, not
from summing children).

Row kinds and path:

| Kind | Path | Source |
|---|---|---|
| `department` | `[dept]` | layout |
| `subtotal` | `[dept, subtotal label]` | data layer |
| `usali` | `[dept, subtotal label, usali]` | data layer value for the leaf USALI |
| `line` | `[…, usali, account_id]` | `workspace_line_rt` |
| `component` | `[…, account_id, component_id]` | loaded on first expand from `planning_get_line`; cached in the store |
| `unmapped` | `['Unmapped', account_id]` | lines whose leaf is the unmapped sentinel |

Statistics lines that are paired with an amount line are **not** separate rows; they show in the
Statistics view on the amount line's row. Unpaired stat lines (occupied rooms, arrivals) sit under
a Statistics department at the top.

Columns:

1. **Line** (auto group column, pinned left): description, account id in muted text for `line` rows,
   a small badge when `open_suggestions > 0` or `split_mapping`.
2. **How it is forecast** (pinned left on desktop): a chip rendered by an Angular cell renderer.
   `driver_summary` for one component; `n components` for several; a dashed "Top line" chip for
   lines fed by the top line (navigates to the Top line tab). Clicking a chip opens the drawer.
   In Statistics view this column shows the stat unit and the paired stat account.
3. **Months**: one column per period in `periods` (month keys). Closed months get a muted "actual" header tag and
   cell class.
4. **Year**, **vs <compare label>**: the header carries the compare version's label; cells are the
   difference, colored good or bad by row type (revenue up is good, expense up is bad).

View toggle (`ave-button-group`): **Amounts**, **Rates**, **Statistics**.

| View | Month cells show | Editable |
|---|---|---|
| Amounts | `amounts` | no (click opens the drawer) |
| Rates | `primary_values` when `primary_field` is set; otherwise amount ÷ occupied rooms in italics | yes, for open months of `line` rows with `primary_field`, when `editable` |
| Statistics | `stats` (the paired stat line's values) or a dot | no |

Editing (Rates view):

- `editable` callback + AG Grid's number cell editor. On commit, build a `set_period` op
  (`planning.patch.ts`) with the row's `primary_component_id` and `primary_row_version`, and call
  the `apply_patch` command. Clearing the cell sends `value: null`.
- While the call is in flight, show the typed value with a pending style. No other optimistic math.
- On success: apply `changed` and `year_totals` to the store, update rows with
  `api.applyTransactionAsync`, flash the changed cells (`api.flashCells`), refetch subtotals and
  KPIs (they come from the data layer), and replace the row's `primary_row_version` from a refetch
  of that line.
- On a stale-version error: show the message inline, reload the line, drop the edit.
- Overridden months get a marker (bold with a corner dot); a context menu item "Clear month
  override" sends `value: null`.

The grid is read-only when `editable` is false. Height: fill the viewport below the header (not a
fixed `75vh`); loading overlay as in Detailed Financials.

### 6.3 Line drawer

`ave-drawer`, `position="right"`, opened by a chip or line click and by the `line` query param.
Header: description, `account_id → usali`, and when paired, `<unit> → <stat account>`.
Tabs (`ave-tabs`): **Drivers**, **Driver fit**, **Transactions**, **Activity**.

**Drivers** (`planning_get_line`)

- A small `<p-chart>` bar chart: 12 months, actual months in a muted color, forecast months in the
  accent color, the compare version as a line.
- One card per component: label, method tag, origin tag (`agent`, `template`, `seed`), the formula
  with inline `ave-input-number` fields for its parameters, the effective range, its year amount
  and share. Formula layouts:

  | Method | Layout |
  |---|---|
  | `fixed` | `$[amount] every month` (+ spread profile select when annual) |
  | `per_unit` | `<driver> × $[rate]` |
  | `stat_chain` | `<driver> × [ratio] <unit> × $[rate]` |
  | `pct_of` | `[pct] % of <driver>` and, for a set, "Set: <node> · n GLs: a, b, c" with an "Edit set" link (include/exclude checklist → `set_adjust` ops) |
  | `headcount` | `[fte] FTE × [hours] hrs a month × $[rate]`, or `[fte] FTE × $[amount] a month` |
  | `flex` | `$[amount] at <base driver> <driver>, [pct] % fixed` |
  | `schedule` | a 12-month row of amount inputs |
  | `manual` | a 12-month row of inputs |
  | `feed` | read-only: "From <source>. Edit days in Top line." |

- Each committed input sends one `set_param` (or `set_period`) op. Inputs are disabled when not editable.
- **Add component**: a small form (label, method, driver picker, parameters, effective from).
  The method list, labels and which parameters each needs come from the `planning_method` catalog;
  the formula layouts above are coded per method key.
  The driver picker offers: Occupied rooms (the model's set), Rooms available, Days, the line's
  department revenue, Total revenue, the paired stat line, and "Another line or total…" (search over
  lines and USALI nodes).
- **Change from a date**: on a component, "New value from…" asks for a month and the new parameter,
  and sends `end_component` + `add_component` in one patch. This is the "new laundry price from
  June 1" flow.
- A bar showing the fixed share (`fixed_share`) versus the share that moves with volume or revenue.
- "From the <template> standard" note when `inherited_from` is set.
- On a fork, parameters changed in the fork carry a "changed here" tag, and a warning tag when
  `source_moved`.

**Driver fit** (`planning_get_driver_fit`)

- Three figures: average error, bias ("drivers run high / low"), worst month.
- A `<p-chart>`: actual as bars, predicted as a line, 12 months.
- A caption: "Today's drivers applied to the actual volumes of <first> to <last>. The figures are
  calculated by the engine."
- If an open `planning.suggestion` of kind `fit` or `ratio_drift` exists for the line, show it as a
  card (title, body, the engine `score`, impact) with Apply / Edit / Dismiss
  (the `resolve_suggestion` command). Otherwise show "No suggestion for this line." Do not derive a
  suggestion in the browser, and do not display `candidates`; they are for the agent.
- Lines fed by the top line show: "This line comes from the top line. Its accuracy is tracked per
  locked forecast in Forecast Accuracy." with a link.

**Transactions** (`planning_get_line_transactions`)

- Month picker (default: last closed month). Table: date, vendor, invoice, description, amount,
  matched component. Unmatched rows are highlighted; rows with an open suggestion carry a tag.
  Footer: the month's total and the month's actual, with the difference if they do not tie.
- Empty state when the hotel has no ledger feed: "Transaction detail is not connected for this hotel yet."

**Activity** (`planning_get_change_log` with `line_id`)

- Newest first: who (person, "Forecast agent, approved by <name>", "Autopilot under <policy>"),
  when, `summary`, reason, and an evidence link when present.

## 7. Version catalog (shared)

`VersionCatalogService`:

- `load(codes: string[], year?: number)` → `financial_cube_get_available_versions`, cached per
  code-set and year for the session, with `refresh()`.
- `groups$`: options grouped as Actual, Forecast (official, newest first), Budget, Custom scenarios,
  Proforma, Comparisons (`latest_forecast`, `ly_actual`, …), each `{ key, label, isLive, isLocked, hasData }`.
- Applies the existing `withProformaOption(options, isMgmtUser)` rule from `src/domain/versions.ts`.

Use it for the planner's Compare select from the start. Then replace the hard-coded lists
(`src/domain/versions.ts`, `forecast.ts`, `constant.enum.ts`, and `buildVersionGroups` in GL
Explorer) screen by screen, in this order, each as its own PR:

1. Detailed Financials top filters (monthly, multiperiod, multi-column, manage-columns dialog)
2. Financial Rollup
3. Major Variance
4. GL Explorer
5. Benchmarking P&L, Exec custom base, Acquisitions deal comps

A screen is converted when its picker shows custom scenarios and the working forecast for hotels
that have them, labels are unchanged for existing versions, and its existing specs still pass.
Stored codes are lower case; keep lower-casing before sending.

## 8. Formatting

The shared `formatNumber` renders 0 as `-` and puts a space after the prefix. An editable grid needs
zero to look like zero. `planning.format.ts`:

- Amounts: whole dollars with thousands separators, no symbol, in cells; negatives in parentheses.
- Zero renders `0`. Null (line not enabled that month) renders a middle dot.
- Rates: 2 decimals with `$`; ratios: up to 4 decimals trimmed; percents: 1 decimal with `%`;
  statistics: whole numbers.
- Differences: explicit sign, colored by a `goodWhenUp` flag from the row type.
- Month headers: `LLL` (and `LLL yy` when the range spans two years).

## 9. Small screens

Follow Plans & Actions: grid at 900px and wider (`window.matchMedia`), a list below that.

- Under 900px the workspace is a read-only list: department → subtotal → line, each row showing the
  year amount and the difference from the compare version; tapping a line opens the drawer
  full-screen with all four tabs. Parameter inputs in the drawer still work.
- Top line under 900px: the monthly table (rooms, ADR, revenue by month). The daily grid shows a
  message to use a larger screen.
- Chart of accounts and Inbox are simple lists and work at any width.

## 10. Scenario dialogs

**Save as** (the `create_scenario` command), `ave-dialog`:

- Source: the open scenario (shown, not editable).
- Type (`ave-radio-group`): **Fork** "follows <source>; keeps only its own changes",
  **Copy** "independent; still takes actuals", **Snapshot** "fully locked; does not change even when
  actuals arrive".
- Name (required; unique within the company).
- A line showing `Custom scenarios used: n of 5`. At 5, disable Save and say "Archive one to save another."
- On success, switch to the new scenario.

**Lock** (the `lock_official` command), for people with `can_lock`:

- Choices: "Monthly forecast (Forecast N)", "Weekly revision (Forecast N.M)", "Budget <year>" (only
  when a budget draft is open). Show the version the lock will write and what it replaces.
- If the call fails with the "was loaded from a file; confirm to replace it" message, show a
  confirmation step inside the dialog (the viewer never shows `confirm()`), then call again with
  `replace_loaded: true`.

**Fork changes** (`planning_get_fork_changes`): a list of the fork's changes with the source's value
then and now, a warning tag when `source_moved`, and "Remove change" (an op that clears it).
"Detach from <source>" → the `detach_fork` command after an in-dialog confirmation.

**Archive**: in the scenario switcher's menu for custom scenarios; in-dialog confirmation;
the `archive_scenario` command.

## 11. Top line

`planning_get_top_line(property_code, scenario_id, month)`.

- A grain indicator from the model (`top_line_grain`); people with `can_update_model` can change it in a settings popover
  (the `set_model_settings` command).
- **Monthly grain:** a table with months as columns and, per segment row (often just Total): Rooms,
  ADR, Revenue; plus Occupancy and RevPAR for the total. Rooms and ADR are editable for open months
  (the `set_top_line_cells` command with month keys).
- **Daily grain:** an AG Grid with days as columns (weekday and date in the header, weekends
  tinted, closed days and days with daily actuals muted) and segments as rows, grouped Transient,
  Group, Contract. A metric toggle: Rooms, ADR, Revenue. Rooms and ADR are editable for open days.
  Each segment row shows its source as a tag (IDeaS, Duetto, Manual).
  Footer rows: Total rooms, Occupancy, On the books, RMS forecast, ADR, Revenue.
  Cell edits are batched: collect edits for 800 ms after the last keystroke-commit, then send one
  `set_top_line_cells` call.
- Tools (buttons, each with an in-dialog form): "Fill from RMS" (`mode: feed`), "Copy last year,
  same weekday", "Spread a month target".
- After any change, a line under the grid: "<Month>: <rooms> occupied rooms at $<ADR>. <n> lines in
  the workspace depend on this." (count of `changed` lines outside the top line.)
- Month navigation with `ave-date-picker` (`view: 'month'`), synced to the `month` query param.

## 12. Chart of accounts

**Hotel chart** (`planning_get_hotel_chart`), an AG Grid at 900px and wider, cards below:

- Filter (`ave-button-group`) with counts: All, Enabled, Off, Needs attention. Search box.
- Columns: Account (description + id), Type (department · category), Last actual, Trailing 12,
  Driver when enabled, In forecast and budget, Note.
- The status cell is a toggle for people with `can_update_chart` when `can_enable`; otherwise a "Not available" tag with
  `blocked_reason` in words ("Not mapped to a Singlepane line", "Balance sheet account", "Retired
  by <operator>").
- Toggling opens a small popover asking for the effective month (default: first open month), then
  calls the `set_account_enabled` command. Enabling shows the driver it will be created with.
- Rows with `attention = 'actuals_while_off'` show "Actuals posted in <month> to an account that is off."
- "Add from operator chart": the search box also searches the rest of the operator chart.

**Operator chart** (a second tab shown with `can_read_standard`; editing needs `can_update_standard`;
`planning_get_operator_chart`, server-paged):

- Columns: Account, Department, USALI, On by default, Retired, Default driver, Stat account, Hotels using.
- Row edit dialog → the `upsert_template_line` command. Stat pairing is displayed here but edited by
  Singlepane staff in v1 (assumption A4).
- "Re-apply to a hotel…" → the `apply_template` command.

## 13. Inbox

`planning_get_suggestions(property_code, status_filter)`; filter by Open, Needs an answer, Applied
automatically, Resolved.

Card: mode tag (Suggest, Ask, Autopilot), title, body, evidence (links to the line and, when
present, transaction rows), impact (rest of year, and by month on expand), the engine score when
present.

| Suggestion state | Actions |
|---|---|
| `open` with a patch | Apply, Edit (opens the line drawer with the proposed values pre-filled; submitting sends `edited_patch`), Dismiss |
| `needs_answer` | The question and its `answer_options` as buttons; "Ask someone else" is out of scope for v1 |
| `auto_applied` | "Applied automatically under <policy>." Undo (`action: revert`) |

All through the `resolve_suggestion` command. After Apply or Undo, update the workspace store from the
returned `changed`.

**Policy**: a read-only table of `planning_get_policies` in v1 (Account or scope, Mode,
Limit). Editing policies is a later PR.

**Ask the agent**: a text box that calls the `request_agent` command with `job_type: 'chat_patch'`,
then polls the suggestions list every 10 s for the reply, which arrives as a suggestion with a patch
(preview, then Apply). If the agent service is not deployed, the job stays `queued`; show "The
forecast agent is not available yet." after 60 s. Do not build a separate chat transcript in v1.

## 14. Setup

`planning/setup`, for people who may create a model: pick a hotel the company can see that has no model, pick the operator
standard (template) if more than one, choose horizon (12, 18, 24 months) and top-line grain, then
the `create_model` command. The call can take several seconds; show progress text, then go to the
hotel's Chart of accounts with the Needs attention filter on.

## 15. States every screen handles

- Loading (`div.sp-state role="status"` pattern), empty, and error (`ave-message severity="danger"`
  with the backend's message through `toUserMessage`).
- Not allowed: a full-page message with a link back to `/exec`.
- Read-only: no inputs, no toggles; banners per §5.
- Session expiry is handled by `ZeusService`; do not add handling.

## 16. Tests

Specs beside the code, fixtures in `planning.testing.ts`:

- `planning.mappers.spec.ts`: API rows to tree rows, including split mappings, unpaired stat lines
  and the unmapped group.
- `planning.format.spec.ts`: zero, null, negatives, percents, differences.
- `planning-api.service.spec.ts`: `run()` builds the mutation, returns its row, and surfaces a
  mutation error's message unchanged.
- `planning-client.service.spec.ts`: requests go to the planner endpoint with the session token;
  an expired session is handled as `ZeusService` handles it.
- `planning.patch.spec.ts`: each op builder; "new value from a date" produces `end_component` + `add_component`.
- `planning-workspace.store.spec.ts`: applying a patch result updates lines and year totals; a
  stale response is ignored; a stale-version error reloads the line.
